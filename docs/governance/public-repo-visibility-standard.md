# Public Repo Visibility Standard

## Status

Active governance standard  
Purpose: preserve Sharpe Nova OS public legibility while protecting internal operating memory

## Canonical Rule

Public repo shows the proof surface.  
Private OS preserves the operating memory.

## Public Repo Purpose

The public repo exists to show that Sharpe Nova OS is a coherent, bounded, non-authority pre-execution governance review layer.

It should help serious readers understand:

- where Nova sits
- what Nova returns
- who reads Nova's output
- what decision Nova supports
- what Nova does not do

## Public Repo Boundary

Agent prepares action.  
Nova structures review context.  
Local authority decides.  
Nova does not execute.

## Public by Default

- README
- START_HERE
- Where Nova Sits
- First Use Case: Agent-Prepared Treasury Action
- Pre-Action Context Contract
- Phase 1 Offline Proof Chain
- high-level architecture
- doctrine lint
- boundary-safe examples

## Controlled Public

- chronology standards
- source reconciliation standards
- institution-owned governance chronology
- governance-context rot
- GTM comprehension testing

These may remain public but require careful language review.

## Private or Not Public by Default

- raw living OS working memory
- Reflex Memory candidates
- unaccepted chronology
- private CCO notes
- internal GTM strategy
- content engine prompts
- market signal logs
- buyer objection logs
- pricing strategy
- allocator-specific strategy
- live operational decision traces
- security-sensitive API behavior

## Forbidden Public Framing

Sharpe Nova OS must not be framed as:

- an approval engine
- an authorization layer
- a payment rail
- a wallet
- a signing tool
- a settlement layer
- a trading system
- a portfolio optimizer
- a compliance product
- an audit system
- an agent supervisor
- a treasury execution system
- an autonomous financial brain

## Final Rule

The repo should prove Nova is real and disciplined.

It should not expose the full operating nervous system of Sharpe Nova OS.

## Pull Request Visibility Discipline

Public-facing changes should use the repository pull request checklist before merge.

The checklist operationalizes this standard by requiring:

- file visibility classification
- canonical boundary preservation
- unsupported claim review
- memory-language safety
- CCO review when required

See:

- `.github/pull_request_template.md`
